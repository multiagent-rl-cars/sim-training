SB3 versus RLlib: what actually justifies either?

The current “multi-agent” implementation trains one shared PPO policy, with cars in a shared arena represented through vectorized environment slots. That is a legitimate baseline, but it is not an opponent league, centralized-critic system, or communication architecture. The distinction is visible in the environment definition and PPO construction.

My recommendation:

FrameworkWhy I would use it hereWhat would justify adopting it
SB3Relatively approachable implementation; existing checkpoints and baseline; straightforward single-policy experiments.Keep it for reproduction and initial debugging. Don’t force every future experiment through its single-agent-oriented interface.
skrlIsaac Lab already documents multi-agent IPPO/MAPPO workflows. MAPPO adds a centralized training critic while retaining decentralized actors.Leading candidate for cooperative driving, communication experiments, and transfer.
RLlibExplicit agent-to-policy assignments, frozen/trainable policies, self-play examples, and distributed collection.Prefer it if opponent populations, heterogeneous policies, or self-play become the immediate research focus.

Those distinctions are supported by the SB3 paper, Isaac Lab training interfaces, and RLlib’s multi-agent documentation.

RLlib is not automatically the faster or more scalable choice for this simulator. Its current documentation still flags limitations around vectorizing multi-agent environments; we would need to verify how its collection model interacts with Isaac’s GPU batching. More infrastructure can also make debugging a single bad transition harder.

For your particular interest in understanding the learning machinery, TorchRL deserves consideration: its collectors, data structures, networks, and losses are exposed explicitly. The cost is taking more responsibility for assembling and validating the training loop. I would consider it if novel model/loss design becomes the research contribution—not add it as a fourth backend immediately. TorchRL’s multi-agent PPO tutorial

My default: preserve SB3, then conduct one small skrl IPPO/MAPPO integration experiment. Choose RLlib instead if self-play populations are the first committed direction. We should not implement four trainers during the cleanup.

Also, PPO versus SAC is a separate decision from SB3 versus RLlib. PPO is reasonable when simulated interactions are plentiful. Real-car interactions are expensive, so replay-based algorithms and demonstration-assisted initialization deserve comparison. Ordinary SAC is not automatically suitable for arbitrary offline datasets, and a PPO checkpoint cannot simply resume as SAC. SB3 algorithm guidance

Isaac versus Gazebo: retain Isaac, but challenge why we need it

Isaac’s strongest justification is batched simulation, tensor-based learning interfaces, domain randomization, and sensor simulation—not inherently more accurate cars. Isaac Lab architecture

A particularly important finding: our current policy does not consume a realistic camera pipeline each step. It uses cached track imagery transformed using simulator pose, with synthetic other-car imagery. That bypasses much of the real perception problem. See observation generation.

Consequently, “NVIDIA has better graphics” is not a convincing explanation for why this task currently needs Isaac.

Gazebo becomes attractive if we adopt a ROS-centered robot system and want to exercise its nodes, messages, sensors, and control interfaces. Our existing camera/Python/serial/ESP-NOW stack does not establish that requirement. Switching would introduce integration work without evidence of better transfer. Its Mac support also has caveats; it is not an automatic local-development solution. Gazebo ROS integration, platform support

I recommend:

  • Retain Isaac for historical comparison and GPU experiments.
  • Add a small, transparent planar car simulator for local closed-loop debugging: measured steering response, throttle dead zone, delay, noise, and track geometry.
  • Consider MuJoCo later if locally inspecting articulated physics and contacts becomes important. It supports macOS, but changing engines still does not identify the physical car’s dynamics. MuJoCo overview

The simple simulator must advertise its limitations. Passing its tests will not establish accurate tire slip, contact behavior, or real-world transfer.

One maintenance issue: NVIDIA now marks our pinned Isaac Sim 5.1 release unsupported. Preserve that environment for reproduction, but validate a supported runtime separately. Mixing a simulator upgrade with reward and model changes would destroy our ability to explain the result. NVIDIA’s support notice

What the architecture needs to make understandable

The biggest structural change should be a lightweight shared model/task package that imports without Isaac.

There is already evidence that this boundary is missing: the real-training repository creates fake Python module paths to load the simulator’s feature extractor. That is checkpoint coupling leaking across repositories. Checkpoint compatibility shim

The shared package should own:

  • Observation definitions: units, coordinate frames, normalization, history, masks.
  • Policy networks and portable inference artifacts.
  • Action definitions and calibrated command mapping.
  • Track/route geometry and task semantics.
  • Transition, termination, reset, and trace formats.

Isaac, real hardware, training frameworks, and W&B should connect through explicit interfaces. We need a few useful boundaries—not a universal plugin framework.

Multi-agent data must distinguish independent worlds from cars within a world. That means explicit world IDs, agent IDs, active masks, policy assignments, and separate agent-level versus world-level resets.

For introspection, I want one synchronized timeline:

Sensor / simulated state
  → estimated state → exact policy observation → network outputs
  → selected action → calibrated command → resulting transition
                                              ↘ reward terms / termination

For a failure, you should be able to answer:

  • What did the car actually observe? What information existed only in simulator ground truth?
  • What were the action distribution, value estimate, and normalization statistics?
  • Was the requested action clipped, delayed, or changed by the control mapping?
  • Which reward terms contributed, with what weights and time scaling?
  • Was the failure perception, policy, control, physics, communication, or reset behavior?
  • Can the same observation be passed through another checkpoint locally?

Capture detailed traces for selected episodes and failures; record lightweight summaries elsewhere. Recording every activation and frame continuously would change throughput and produce huge artifacts.

W&B should compare runs and retain selected artifacts. A portable run record should remain usable without W&B. Rerun is worth testing as the synchronized spatial/timeline viewer, after that recording format exists.

The model itself also needs scrutiny. The current feature extractor combines a residual CNN with BatchNorm, a velocity branch, and fused features. We should justify its size, normalization behavior, and temporal inputs through comparisons—not preserve them because they were inherited. Saliency plots can help exploration, but controlled input perturbations and ablations are stronger evidence of what the policy uses.

How your research directions change the design

DirectionFoundation we should build now
Multi-agent transferIdentical actor observation/action contracts across sim and real; communication with explicit delay, dropout, message age, and bandwidth; collision-aware reset lifecycle.
Real-world trainingTimestamped transitions, intervention logging, policy versions, replay datasets, and an actor/learner lifecycle that respects the chosen algorithm’s assumptions.
Self-playPolicy identities, matchup configuration, frozen opponents, outcome metrics, and held-out cross-play—not merely “two cars receive rewards.”
Harder tracksDirected route graphs, intended exits, lane/rule semantics, and scenario generation. Color should be an experimental observation channel, not the only representation of direction.
ScalingSeparate cars-per-world from world count; profile perception, inference, simulation, radio delay, and stale commands independently. Twenty simulated cars do not validate twenty physical cars.

Three corrections matter here:

MAPPO does not automatically provide communication. A centralized critic can see training-only state while the actors remain local. Learned communication is another model and interface decision.

Self-play does not eliminate objectives. Racing still needs a definition of winning; cooperation needs measurable shared outcomes. It changes where opponents and challenges come from, not whether the task needs specification.

Colored tracks currently lose their distinguishing information in the binary observation path. We should compare binary, semantic-channel, and color observations under matched scenarios rather than simultaneously changing the track, network, and reward.

What I think you are missing

The main missing work is measurement and experimental controls, more than another framework.

  1. System identification before more reward tuning. Measure command-to-speed and command-to-turn response, dead zone, hysteresis, delay, asymmetry, and battery effects. The real vision code’s get_velocity computes displacement rather than time-normalized speed; it cannot simply be assumed equivalent to simulator velocity. Real velocity calculation
  2. A classical controller baseline. Compare RL against a calibrated path follower and simple obstacle/yield logic. Otherwise we cannot tell whether RL improves coordination or merely compensates for a poor control interface.
  3. Evaluation independent of training reward. Track completion, collisions, interventions, wrong-way travel, oscillation, minimum separation, and physical interaction time. Use held-out tracks/conditions and multiple seeds. A higher return is not necessarily better driving.
  4. Reset and safety as explicit system behavior. Resetting is not an invisible administrative step. It consumes time, changes observations, can collide with other cars, and affects sample-efficiency claims. Hardware stop/watchdog behavior must not depend on the learned reward.
  5. Asset and calibration provenance. Some older original USDs have been recovered, but they still need validation. Generated fixtures are not calibrated cars. CAD attachment changes should trigger a mechanical/calibration review, not disappear into an unrelated software commit.
  6. One primary near-term experiment. All five directions can inform the interfaces, but pursuing all five equally would spread the work thin. I would start with measurably reliable two-car obstacle avoidance and transfer, while making communication and self-play possible later.

The reported 15-minute convergence should remain a reproduction question, not our project’s definition of success.

Tooling and verification

I would adopt a small, deliberate stack:

  • uv: separate locked local-development and Isaac environments.
  • Ruff: replace overlapping formatting/import/lint tools with one configuration. Ruff documentation
  • One type checker: initially Pyright as the gate, with a scoped ty trial on the extracted core. ty is worth evaluating, but its current upstream policy still identifies it as beta with potentially changing diagnostics. Don’t maintain two permanent mandatory checker configurations. ty status
  • pytest plus selected Hypothesis tests: numerical invariants, reset sequences, geometry, observation purity, and contract compatibility.
  • W&B: comparisons, resolved configurations, metrics, selected videos, and artifact lineage.
  • PyTorch profiler: short targeted captures when investigating performance, not always-on tracing. Profiler guide

Typing alone will not catch meters versus pixels, wrong tensor axes, or state mutation.

The existing five tests cover tracking/configuration—not the learning problem. The new verification ladder should be:

WhereWhat we can establish
Mac, ordinary testsGeometry, rewards, units, history/reset behavior, configurations, model forward passes, checkpoint loading.
Mac, recorded data/local simulatorObservation inspection, policy comparisons, closed-loop task logic, communication faults, trace/video generation.
Short GPU integration runActual Isaac imports, physics/rendering, batched resets, one training update, checkpoint/reload, measured throughput.
HardwarePerception accuracy, actuation calibration, latency, safety behavior, and real driving quality.

One concrete source-level test target: observation code takes a tensor slice and modifies it in place, potentially altering cached simulator velocity. Another: current reward telemetry samples the final rollout step rather than aggregating the entire rollout. These are exactly the sorts of problems dashboards alone cannot fix.

For runs, use bounded jobs, periodic checkpoints, a verified artifact handoff, and separate compute shutdown controls. A detached process surviving SSH disconnection is useful; it is not a billing limit. Credentials should be injected as secrets, and the W&B key pasted into chat should be rotated.

The launch sequence should therefore be: preserve the baseline → extract and test contracts → build one inspectable end-to-end experiment → evaluate the next training backend → expand scenarios. Keep structural changes, bug fixes, runtime upgrades, and scientific changes distinguishable.

The earlier refactor plan needs to reflect this broader architecture. The goal is not simply cleaner folders: it is being able to explain a result, reproduce it, and change one important assumption at a time.
