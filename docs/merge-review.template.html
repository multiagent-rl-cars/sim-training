01 / The proposal

Merge a foundation—not a convergence claim.

The strongest reason to merge is not a tidier folder tree or a higher reward curve. It is that mistakes in geometry, configuration, observations, checkpoint handling and experiment attribution can now be isolated and tested without renting a GPU.

We keep the previous team's learning stack and preserve frozen reference code. This is an incremental route toward eight months of multi-agent research, not a rewrite onto an unproven framework.

Recommendation: review and merge the independently tested portable foundation and evidence tooling. The current working tree also contains a new image-amplitude correction that has passed local tests but has not run on the GPU. Either validate its four preregistered GPU gates before merging the whole branch, or land it as a separately reviewed follow-up. Do not treat the existing baseline video as validation of that newer code.

03 / Actual driving evidence

Fewer resets after 15 minutes of training.

The hypothesis was frozen before the run: fewer off-track resets without lower reset-excluded travel in a fixed matched evaluation. The final policy met that rule on the generated circular-track fixture.

What this proves: improvement on one specified fixture and matched seed, plus functioning training/evaluation plumbing. What it does not: the prior team's 15-minute convergence result. These are 12 repeated circles, not 12 held-out tracks. Each final car covered about 0.73–0.81 signed revolutions—not a complete lap. There is no generalization, obstacle-avoidance, coordination or real-hardware claim.

How to read the policy objective

For the Basic fixture with obstacles disabled, reward combines contour proximity, planar speed and an alive term, minus steering magnitude, then multiplies by the control timestep. The contour distance is not established centerline error; the steering penalty is not steering-rate or jerk. There is no explicit lap, route-direction or right-of-way objective. The zero raw action commands forward wheel motion, not a stop.

W&B should show the run while it happens

The canonical config.yaml selects online tracking. The workflow checks credentials and readable project access before starting the GPU workload. Metrics and videos upload from the training host, not through a continuously connected laptop. End-of-run evaluation media and checkpoint artifacts are uploaded automatically by the online experiment workflow. The recovered results below were uploaded from the Mac because the original GPU jobs deliberately ran offline.

Offline mode remains explicit for isolated tests. An online authentication failure stops the launch; it does not quietly turn live monitoring off. Local backups remain required because an upload attempt is not the same thing as verified server ingestion.

06 / Questions a skeptical reviewer should ask

The objections are reasonable.

“The previous team's code worked. Why disturb it?”

Preserve it as a frozen reference, not an implicit standard that cannot be inspected. We retained SB3 and Isaac, archived the baseline, test extracted model equivalence and identify every intentional behavior change. The new run shows that the reference path still executes end to end. It does not prove that the original final training recipe or physical assets have been recovered.

“Did refactoring make the policy better?”

Not established. The before/after video compares initial and trained weights within the same frozen refactored fixture setup. It is not a pre-refactor versus post-refactor ablation. The demonstrated engineering benefit is cheaper inspection, attributable experiments and reliable evidence—not a causal learning-performance advantage.

“Why not switch to RLlib, Gazebo or a different MARL stack now?”

That would change the learner or simulator while we are still establishing the baseline. Keep SB3 for the current shared-policy PPO workflow and Isaac for the inherited GPU/camera environment. Reopen the learner decision for measured needs such as a centralized critic, heterogeneous policies, distributed collection or opponent populations; reopen the simulator decision for a calibrated ROS/control or fidelity requirement. Multi-car integration today is not proof that SB3 already solves future self-play or communication.

“Hundreds of tests can still validate the wrong assumptions.”

Agreed. The suite deliberately separates invariants and compatibility from runtime integration and policy quality. Independent reviewers inspect the assertions, fixture provenance and failure cases. Known history/ego/timing defects remain tracked instead of being hidden behind a green test count. Next tests must include direction/lap/collision metrics, held-out starts/tracks and paired seeds.

“Is this too much infrastructure for a small team?”

The core path is one YAML file, self-contained profiles, one runner and a report. One dependency lock covers CPU and simulator options. W&B can name runs automatically; explicit output folders are optional. Offline recovery belongs in operational support, and dated analysis belongs with its experiment. Compatibility and provenance still have maintenance costs; keep them only where tested contracts protect real workflows.

“Are we ready for real cars, intersections or self-play?”

No. This foundation makes those experiments easier to specify, not already solved. Real training needs calibrated low-speed control, latency measurements and supervised safety/reset rules. Intersections need route/direction semantics. Coordination and self-play need explicit agent/policy/communication contracts and appropriate evaluation. CAD attachment repair is a separate hardware task.

07 / An actionable merge decision

Review in layers. Keep the acceptance bar narrow.

  1. Freeze the proposed diff. Commit the reviewed source and manifests after checking the dirty working tree for unrelated changes. This page does not commit, push or merge anything.
  2. Review the portable extraction separately. Check dependency direction, numerical/model parity, intentional velocity correction and legacy checkpoint expectations.
  3. Review experiment integrity and operations. Re-run CPU gates; inspect requested/resolved configs, failure retention, explicit online tracking, backup verification and bounded job supervision. Include the new YAML and W&B changes in the reviewed manifest.
  4. Resolve the v3 boundary before full-branch approval. Run the four image-contract GPU gates against the preregistered reference using the exact proposed source snapshot, or separate that correction into a follow-up. The older GPU result cannot be inherited by newer source or by the new launcher.
  5. Merge the foundation with a documented backlog. Acknowledge the image/history/ego/reset and historical-asset limits. Next research claim: longer, full-lap and held-out evaluations with paired seeds—not an unbounded sweep.

What “merge” should mean

A reviewed, reproducible starting point for future work, with explicit supported commands, tests and evidence boundaries.

What it must not mean

“Bug-free,” original results reproduced, real-world ready, all eight months of infrastructure complete, or blanket approval for unattended GPU spend.
